## 1. Release Executive Summary

**Homebase v1.0.6** is a performance, correctness, and reliability release focusing on dashboard startup optimization, off-thread wallpaper poster encoding, validated startup poster reuse, and robust wallpaper persistence across browser tabs.

Key updates in this release:
1. **Off-Thread Poster Encoding**: Eliminated synchronous main-thread blocking tasks caused by `canvas.toDataURL()` during wallpaper poster generation by introducing asynchronous canvas encoding (`canvasToDataUrlAsync`) using `canvas.toBlob()` and `FileReader.readAsDataURL()`.
2. **Validated Cached Poster Reuse**: Reuses existing valid startup poster data URLs immediately on launch, verifying target URL, encoding version, and source revision before encoding to prevent redundant startup work.
3. **Forced Regeneration Correctness**: Fixed an issue where forced poster regeneration requests could be defeated by stale reuse logic; forced requests now reliably re-encode and commit fresh poster artwork under current identity.
4. **Authoritative Store Isolation**: `readStoredBundle` inspects extension storage exclusively when available and never backfills or resurrects missing fields from `localStorage` mirrors.
5. **Opaque Revision Support & Intervening Change Handling**: Removed relational numeric ordering assumptions on revisions; accurately detects intervening modifications by concurrent tabs while allowing normal sequential revision updates.
6. **Explicit Persistence Contracts & Preload Mirror Invalidation**: Explicitly checks `HomebaseStorage.setMany` / `browser.storage.local.set` success contracts before updating mirrors. If `localStorage` mirror writes fail partway, all poster keys in `localStorage` are cleared immediately, preventing `preload.js` from accepting mismatched pairs.

## 2. Optimizations & Issues Resolved

### 2.1 Main-Thread Startup Optimization & Off-Thread Canvas Encoding
- **Issue**: Synchronous `canvas.toDataURL('image/webp')` during startup poster creation blocked the main thread for 55–82 ms per conversion, delaying first-paint responsiveness.
- **Resolution**:
  - Implemented `canvasToDataUrlAsync(canvas, type, quality)` utilizing asynchronous `canvas.toBlob()` and `FileReader.readAsDataURL()`, with graceful fallback to `canvas.toDataURL()` if `toBlob` fails.
  - Updated `createOptimizedPosterDataUrl` to await off-thread encoding across both `createImageBitmap` and `Image` paths.

### 2.2 Cached Poster Reuse & Identity Separation
- **Issue**: Startup initialization unconditionally re-encoded wallpaper posters on every launch even when a valid, correctly-sized poster data URL was already cached. In-flight generation also risked premature storage updates.
- **Resolution**:
  - Added `isValidStartupPosterDataUrl(dataUrl)` verifying valid format and size boundaries (length <= 240,000 characters).
  - Validates cached output against `targetEncodingVersion` and `targetRevision`. If a matching, valid cached poster exists, it is reused immediately without re-encoding.
  - Storage is kept untouched during pending generation, ensuring committed output identity remains separate from in-flight generation identity.

### 2.3 Forced Regeneration & Production Identity Alignment
- **Issue**: A forced regeneration request could be bypassed by a trailing reuse branch that returned previous cached output under the same URL. Production revision fields also lacked unified handling across upload and replacement paths.
- **Resolution**:
  - In `wallpaper-controller.js`, forced generation requests bypass cache reuse and commit newly generated output when still current.
  - Aligned production identity with actual upload keys: uploads in `gallery-ui.js` receive unique persistent IDs and cache keys. Removed synthetic fallback fields and forwarded caller options through `applyWallpaperByType`, `setWallpaperFallbackPoster`, and `cacheAppliedWallpaperPoster`.

### 2.4 Authoritative Storage Isolation & Opaque Revisions
- **Issue**: `readStoredBundle` merged fields from extension storage and `localStorage`, risking stale mirror resurrection when metadata was cleared. Relational revision comparisons (`>`) broke on opaque strings or UUIDs.
- **Resolution**:
  - Reads evaluate authoritative extension storage first; missing fields are never backfilled from mirrors. `localStorage` is only queried in environments lacking extension storage.
  - Evaluates opaque revision changes by distinguishing initial stored state, target requested revision, and intervening storage state, allowing sequential updates while preventing stale tasks from overwriting newer intervening commits.

### 2.5 Explicit Persistence Outcomes & Preload Mirror Invalidation
- **Issue**: Storage write failures did not consistently prevent mirror updates, and partial `localStorage` quota failures could leave mismatched URLs and data URLs for `preload.js`.
- **Resolution**:
  - Validates `HomebaseStorage.setMany` results (`res && res.success && (!res.rejectedKeys || res.rejectedKeys.length === 0)`). Aborts and returns `false` if authoritative write fails.
  - In `wallpaper-storage.js`, mirror updates are wrapped in a `try...catch` block. If writing to `localStorage` fails partway (e.g. `QuotaExceededError`), all poster mirror keys are immediately removed, guaranteeing `preload.js` will not pair mismatched URLs or stale data.

- **Preserved Manual Verification Scope**: Previous manual check confirmations remain as recorded; release authorization does not constitute confirmation that additional manual checks passed.
- **Store Publication Boundaries**:
  - The source and GitHub release baseline (`1.0.6`) is strictly distinct from published browser store packages (Firefox AMO `1.0.4` live; Chrome Web Store `1.0.2` live, `1.0.4` under review; Edge `1.0.2` in review).
