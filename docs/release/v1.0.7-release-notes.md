## 1. Release Executive Summary

**Homebase v1.0.7** is a critical stability and reliability release addressing cross-tab dashboard synchronization, multi-tab startup performance, and video wallpaper tab-switching lifecycle management.

Key updates in this release:
1. **Multi-Tab Startup Reliability & Freeze Elimination**: Resolved a critical issue in multi-tab workflows (notably observed in Firefox) where having three or more dashboard tabs open caused tabs to stall indefinitely at startup with unresponsive search and controls (occurring even when tabs were opened slowly). This was caused by an uncontrolled cross-tab storage write cascade on `appShowSidebar`, which flooded browser IPC channels with thousands of redundant writes.
2. **Non-Persisting Storage Hydration & Sync**: Applied explicit non-persisting flags (`{ persist: false }`) during initial settings hydration and incoming cross-tab storage changes, breaking feedback loops while preserving full live preview, transactional Save persistence across reloads, and clean Cancel restoration.
3. **Settled Cancelled Wallpaper Loads**: Enhanced wallpaper source-loading lifecycle management by tracking scheduled callbacks (`requestAnimationFrame` and `setTimeout`) and explicitly settling pending source-load tasks immediately when a tab is hidden or a wallpaper change supersedes the active task, eliminating reliance on suspended animation frames in background tabs.
4. **Guarded Wallpaper Playback Resumption**: Added strict sequence tokens, start sequence checks, and wallpaper selection identity revalidation in `resumeWallpaperPlaybackIfEligible()`. Returning to a tab cleanly resumes live video without duplicate playback setups, stale media playback, or audio glitches.
5. **DOM Autoplay Removal**: Removed the DOM `autoplay` attribute from background video elements in `src/new-tab.html`, ensuring media elements never start uncoordinated background decoding before controller visibility and readiness checks complete.

## 2. Optimizations & Issues Resolved

### 2.1 Multi-Tab Startup Freezing & Cross-Tab Sidebar Storage Feedback Loop
- **Issue**: Having three Homebase tabs open in Firefox (even when opened slowly) caused subsequent tabs to become unresponsive (stalled at `preload bookmarks-booting`, typing in search worked natively but suggestions never loaded, Enter reloaded the raw HTML page, dock and settings buttons failed to respond, and extension storage calls timed out >3000ms across all open tabs).
- **Diagnosed Root Cause**:
  - During startup hydration, `loadSettingsStorage()` read `storedShowSidebar` and invoked `applySidebarVisibility(storedShowSidebar)` without `{ persist: false }`. Because `applySidebarVisibility` defaulted persistence to `true`, every dashboard launch wrote `appShowSidebar` back to extension storage.
  - When multiple tabs were open, writing `appShowSidebar` triggered `browser.storage.onChanged` in other open tabs.
  - In `src/newtab/settings/settings-preferences.js`, `handleSettingsStorageChange` received `changes[APP_SHOW_SIDEBAR_KEY]` and called `applySidebarVisibility(nextSidebar)` without `{ persist: false }`, immediately writing `appShowSidebar` right back to storage.
  - Between multiple open tabs, this created an exponential IPC ping-pong cascade (>6,450 writes within seconds), ballooning in-flight queue depth to over 1,550 pending IPC messages.
  - When subsequent tabs opened, their initial storage requests (`loadFolderMetadata`, `loadBookmarks`) queued behind thousands of pending writes, stalling `initializePage()` before event listeners could attach.
- **Resolution**:
  - In `src/newtab/settings/settings-preferences.js`, passed `{ persist: false }` to `applySidebarVisibility` in `handleSettingsStorageChange` (aligning with all other widget preference handlers).
  - In `src/newtab/settings/settings-storage.js`, passed `{ persist: false }` to `applySidebarVisibility` in `loadSettingsStorage` and `updateSettingsState`.
  - Reviewed and removed a speculative in-memory `changed` guard in `applySidebarVisibility` to prevent suppressing legitimate retries or explicit saves, maintaining caller-driven `{ persist: false }` semantics.

### 2.2 Wallpaper Lifecycle: Settled Cancelled Loads & Playback Resumption Guard
- **Issue**: Switching between active and background tabs while a video source load was pending could leave operations awaiting browser-suspended animation frames, or allow delayed resume callbacks to restart a stale wallpaper after the user changed selections. Background video elements with the DOM `autoplay` attribute also risked initiating media decoding before visibility was established.
- **Resolution**:
  - Removed `autoplay` attribute from both `.background-video` elements in `src/new-tab.html`.
  - In `src/newtab/wallpaper/wallpaper-controller.js`, implemented `createSourceLoadOperation()` to track scheduled animation frames and timers. On tab hide, superseding source selection, video clear, or playback cleanup, pending callbacks are explicitly cancelled and task promises are settled immediately without waiting for animation frames.
  - In `setBackgroundVideoSources()`, when `document.hidden` is true, DOM video loading (`v.load()`) is deferred while keeping the poster image synchronized. Video source loading is initiated only when the tab returns to visibility.
  - In `resumeWallpaperPlaybackIfEligible()`, after `await setBackgroundVideoSources()`, validates `resumeSequence`, `wallpaperVideoStartSequence`, selection identity (`id`, `videoUrl`, `posterUrl`), wallpaper type, tab visibility, and Performance Mode before modifying `lastAppliedWallpaper` or starting video playback. Stale resumes cannot overwrite newer wallpaper selections or start stale playback.
